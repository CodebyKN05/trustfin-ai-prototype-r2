Abstract
TrustFin AI is a completed loan decision-support system that combines product-speciﬁc
credit prediction with post-hoc explanations and quantitative checks on those explanations.
The project addresses a practical limitation of using complex models for lending: a prediction
can be useful for ranking risk while remaining diﬃcult for an applicant or reviewing oﬃcer
to interpret. A single explanation is also not suﬃcient evidence that the explanation is
faithful, stable, consistent across methods, or insensitive to a protected characteristic.
The implemented system supports home-loan and personal-loan applications. Each prod-
uct uses a separately trained XGBoost classiﬁer and a product-speciﬁc preprocessing pipeline.
Derived repayment features include monthly instalment and ﬁxed-obligation-to-income ra-
tio (FOIR); the home-loan pipeline also derives loan-to-value ratio. The prediction service
returns the model decision and class probability, and produces local explanations using Tree-
SHAP and tabular LIME. An explanation-validation stage calculates faithfulness, stability
under a small seeded perturbation, top-feature consistency between SHAP and LIME, and
an individual counterfactual gender-ﬂip score. These values are combined using documented
weights to form a composite Trust Score. The result, selected applicant ﬁelds, explanation
data, and trust measures can be stored through SQLAlchemy using local SQLite or a conﬁg-
ured PostgreSQL database. A React dashboard presents results to applicant and bank-oﬃcer
views and the backend can generate a PDF report.
The project datasets are generated by repository scripts and contain 3,000 records each;
they are not records from a lending institution. On the stored stratiﬁed test evaluations, the
home-loan model reports 97.00% accuracy and 0.9978 ROC-AUC, while the personal-loan
model reports 97.33% accuracy and 0.9963 ROC-AUC. These values describe performance
on generated data and do not establish performance on real applicants. The composite score
is an engineering indicator deﬁned by the project, not an independently validated measure
of safety or lending quality.
The report therefore distinguishes predictive performance,
prediction conﬁdence proxy, explanation checks, and real-world fairness evidence.
Keywords: Explainable AI, credit scoring, XGBoost, SHAP, LIME, explanation validation,
fairness, Trust Score.

Chapter 1
Introduction
1.1
Introduction
TrustFin AI is a group project that studies how local explanations and explanation checks
can be included in a loan decision-support application. The system accepts an applicant
proﬁle, selects a home-loan or personal-loan model, returns a binary approval prediction
and probability, and generates SHAP and LIME explanations. Four validation values are
then calculated and combined into a composite Trust Score. Results are presented through
a browser dashboard and can be stored for later review.
The central concern is not simply whether a classiﬁer can produce a high score on a
test split. In a consequential setting such as credit assessment, users also need to under-
stand what information inﬂuenced an output and whether a generated explanation behaves
consistently under deﬁned checks. TrustFin AI therefore treats explanation quality as a
measurable part of the workﬂow. It does not treat the resulting Trust Score as proof that a
lending decision is correct, fair, or suitable for deployment.
1.2
Background
Credit scoring uses applicant and account information to estimate the likelihood of a credit
outcome. Statistical classiﬁcation has been used for consumer credit for decades, with studies
comparing a range of classiﬁcation methods and discussing domain-speciﬁc problems such
as incomplete applicant histories and reject inference [1, 2]. Modern ensemble methods can
model non-linear interactions in structured records, but their internal logic is less direct to
communicate than a small scorecard or decision tree.
An explanation method attempts to summarize a model’s behavior for a particular input.
SHAP assigns feature contributions using a Shapley-value framework, while LIME ﬁts an
interpretable approximation around an instance. These methods answer related but not
identical questions and can disagree. Moreover, an explanation that looks plausible is not
necessarily faithful to the model, robust to small input changes, or neutral with respect

to a protected feature. Research has therefore examined explanation quality as a separate
evaluation problem rather than assuming that an explanation is valid merely because it was

1.3
AI in Financial Decision-Making
Structured credit data are a natural setting for supervised classiﬁcation: records contain
numerical ﬁelds such as income, requested amount, repayment term, and credit indicators,
together with categorical attributes. TrustFin AI uses XGBoost for its two product-speciﬁc
models. The model provides a decision and a probability for the approval class. In the
application, the probability associated with the selected class is also returned as a conﬁdence
representation.
Automated or model-assisted ﬁnance requires attention to the complete decision path.
Input handling aﬀects what the model receives; preprocessing aﬀects feature scale and rep-
resentation; a prediction probability is not the same as an explanation; and an explanation
is not an audit of model fairness. A useful decision-support interface should preserve these
distinctions and show enough information for an oﬃcer or applicant to understand the re-
sult. General risk-management guidance likewise emphasizes that system risks depend on
context and should be considered throughout development and use [5].
1.4
Motivation
The project was motivated by three connected needs. First, applicant-facing systems should
communicate the factors associated with a model output in accessible language. Second, a
single explainer may not be a suﬃcient basis for review, so the application should compare
SHAP and LIME outputs and report diﬀerences. Third, explanation quality should be as-
sessed along more than one dimension: whether inﬂuential features aﬀect the model output,
whether rankings persist after a small perturbation, whether two methods select similar
leading features, and whether a protected-attribute counterfactual changes the probability.
The motivation is deliberately limited. The repository contains generated datasets and
experimental model artifacts, not production lending records. TrustFin AI demonstrates
an engineering workﬂow for prediction and explanation review; it is not a validated credit
policy or a substitute for institutional model governance and human review.
1.5
Aim of the Project
The completed project delivers a loan decision-support system that produces product-
speciﬁc predictions, presents local model explanations, and calculates deﬁned checks on
the generated explanations before displaying a composite explanation-reliability indicator.

1.6
Objectives
The project objectives are:
1. prepare separate feature pipelines for home-loan and personal-loan records;
2. train and evaluate XGBoost classiﬁers using ﬁxed train-test partitions;
3. integrate SHAP and LIME explanations for individual prediction requests;
4. calculate faithfulness, stability, explainer consistency, and individual counterfactual fair-
ness scores from the implementation;
5. combine the four values using the implemented weighted formula and return a prediction-
conﬁdence representation;
6. expose the workﬂow through a React interface and FastAPI service, with evaluation
persistence and PDF reporting.
1.7
Scope
The implemented scope includes home-loan and personal-loan application forms, their trained
models and engineered ﬁnancial features, single-record prediction, SHAP and LIME expla-
nations, four explanation checks, composite Trust Score, SQLite/PostgreSQL persistence,
batch CSV processing, evaluation history, and PDF report generation. The interface pro-
vides applicant and bank-oﬃcer views; these are presentation modes selected in the client,
not authenticated accounts.
The project does not implement a real lender integration, a production underwriting pol-
icy, secure user authentication, population-level fairness monitoring, probability calibration,
or an independently validated Trust Score threshold. The interactive what-if calculator is a
deterministic aﬀordability scenario, not a live call to the prediction model. Fraud detection
and unrelated ﬁnancial products are outside the scope.
1.8
Implemented Approach
The implemented workﬂow is: collect a product-speciﬁc application; validate and normalize
request ﬁelds; engineer repayment features; transform ﬁelds using the product preprocessor;
obtain an XGBoost decision and probability; compute SHAP and LIME local explanations;
evaluate four explanation properties; calculate the weighted Trust Score; return a structured
response; and present, persist, or export the result. This sequence is expanded in Chapters
4 and 5.

Chapter 2
Literature Survey
2.1
Introduction
This chapter reviews work relevant to the implemented system: consumer credit classiﬁca-
tion, gradient-boosted trees, post-hoc local explanation, objective explanation checks, and
fairness measures. The focus is on concepts used to motivate or interpret TrustFin AI. The
project does not claim to introduce new versions of SHAP, LIME, or the fairness criteria in
the literature.
2.2
Machine Learning in Loan Approval
Hand and Henley surveyed statistical classiﬁcation methods used in consumer credit scoring
and described issues speciﬁc to credit data, including the limited public availability of lending
datasets [1]. Later benchmarking work compared a large set of classiﬁers across multiple
credit-scoring datasets, showing why model choice should be assessed empirically rather
than inferred from a single algorithm’s reputation [2]. These studies provide context for
using supervised learning while also highlighting the importance of dataset properties and
evaluation design.
Gradient boosting builds an additive model by ﬁtting successive learners to reduce a loss
function. Friedman formalized gradient boosting as a function-approximation procedure
[6]. XGBoost provides an optimized tree-boosting implementation with regularization and
systems techniques designed for eﬃcient learning on structured data [7]. TrustFin AI uses
XGBoost because it is suitable for its tabular, mixed-type loan records and supports the
selected TreeSHAP workﬂow. This engineering choice alone does not establish superiority
over other classiﬁers; no current product-speciﬁc comparison experiment is stored in the
repository.

2.3
Explainable Artiﬁcial Intelligence
Explainable AI includes methods intended to make model behavior more understandable
to people. Explanations may describe global patterns, local feature attributions, example-
based behavior, or simpler models. TrustFin AI implements local post-hoc explanations for
individual loan records. Such explanations should be interpreted as descriptions of model
behavior under a chosen method and representation. They do not, by themselves, establish
a causal relationship between a feature and repayment or prove that changing a feature
would change a real-world outcome.
2.4
SHAP
Lundberg and Lee presented SHAP as a uniﬁed framework for additive feature attribution,
connecting local explanation methods to Shapley-value principles [8]. In a local additive
explanation, the model output is represented through a baseline and feature contributions.
The sum of contributions is associated with the explained prediction in the chosen output
space. The exact interpretation depends on the explainer, model, and output convention.
TrustFin AI initializes a SHAP TreeExplainer for each loaded XGBoost product model.
For a request, the transformed instance is passed to the explainer and returned contributions
are converted into a common schema containing feature name, value, contribution, and
direction. The dashboard uses these contributions to show leading decision drivers. In this
implementation, the explainer operates on preprocessed model features while the display
path attempts to retain applicant-level values where names align. This mapping should be
reviewed when interpreting categorical one-hot features and engineered columns.
2.5
LIME
Ribeiro, Singh, and Guestrin introduced LIME as a model-agnostic approach that explains
a prediction by ﬁtting a simple interpretable model in the neighborhood of the instance
[9]. LIME’s explanation is local: it depends on the perturbation distribution, similarity
weighting, feature representation, and surrogate ﬁtting settings. It is not a global account
of the classiﬁer.
TrustFin AI initializes a tabular LIME explainer with a transformed background sample
and the model’s transformed feature names. At prediction time the model’s probability func-
tion is passed to LIME. The implementation returns feature contributions in the common
explanation schema. Applicant-speciﬁc deterministic seeds are used to reduce run-to-run
variation in LIME’s sampling for identical inputs. Seed control improves repeatability un-
der this implementation; it does not remove sampling approximation or establish correctness
of a local surrogate.

2.6
Explanation Validation
Explanation quality is multi-dimensional. A feature ranking can appear stable while being
disconnected from model behavior; an explanation can change under small perturbations;
and separate methods can select diﬀerent features.
Yeh et al.
study measures related
to inﬁdelity and sensitivity and show that explanation evaluation involves choices about
perturbations and objective functions [3]. Alvarez-Melis and Jaakkola identify faithfulness
and stability as important explanation desiderata and examine robustness under changes in
input [4].
The TrustFin implementation translates several such concerns into local checks. Its faith-
fulness score masks selected attribution features and compares changes in model probability
against a zero-vector baseline. Stability is measured as a rank correlation between SHAP
contributions before and after seeded Gaussian noise in transformed feature space. Consis-
tency is the Jaccard similarity between top-three SHAP and LIME feature sets. These are
project-speciﬁc operational deﬁnitions. Their scores should not be treated as interchangeable
with every published ﬁdelity, sensitivity, or agreement metric.
2.7
Trustworthy and Fair AI
Fairness can be deﬁned in diﬀerent ways, and metrics may express diﬀerent policy choices.
Hardt, Price, and Srebro formalize equality of opportunity in supervised classiﬁcation in
terms of true-positive rates across groups [10]. TrustFin AI’s live request metric is diﬀerent:
it compares the model’s approval probability for one applicant with the probability after
ﬂipping the gender ﬁeld while holding the remaining normalized proﬁle ﬁxed. That indi-
vidual counterfactual score is not a population-level disparate-impact or equal-opportunity
audit.
The saved training metrics also contain a female-to-male approval-rate ratio calculated
on each generated test split. This is a group-level descriptive statistic for the synthetic
evaluation data, while the online counterfactual score is per applicant.
Neither number
on its own establishes that a deployed credit system is fair. The NIST AI Risk Manage-
ment Framework describes trustworthy-AI characteristics and risk-management activities as
context-dependent and lifecycle-oriented [5]; TrustFin AI is a completed academic imple-
mentation and has not undergone an institutional AI risk-management assessment.
Counterfactual explanations are another related area. Wachter, Mittelstadt, and Russell
discuss explanations framed as changes to facts that could produce a desired result, while
noting technical and normative constraints [11]. TrustFin’s what-if calculator does not im-
plement a counterfactual search algorithm. It adjusts three ﬁnancial inputs and recalculates
an illustrative aﬀordability ratio; it does not query the classiﬁer or guarantee an outcome.

2.9
Research Gap
The literature provides explanation methods and several proposals for evaluating explana-
tions, but no single scalar is universally accepted as a complete measure of explanation
trustworthiness. The project addresses an engineering gap: a working loan-assessment sys-
tem can show two local explanations and attach several explicit checks to each decision.
The contribution is the integration and examination of these checks in a completed system,
not a new theoretical metric or evidence of real-world lending validity.
2.10
Summary
SHAP and LIME provide complementary local explanation mechanisms, while explanation-
evaluation research motivates checking behavior, stability, and agreement separately. Fair-
ness metrics require a clear deﬁnition and a relevant population. These ﬁndings shape the
report’s interpretation: TrustFin AI produces observable model outputs and project-deﬁned
validation scores, but the scores remain limited to the deﬁnitions, data, and perturbations
implemented in the repository.

Chapter 3
Problem Statement and
Requirements
3.1
Problem Deﬁnition
The project addresses the diﬃculty of reviewing a loan model output when the classiﬁer is
more complex than a short rule list. A bare approval or rejection label gives little indica-
tion of which model inputs were inﬂuential, and one post-hoc explanation does not show
whether the explanation is robust or consistent with another method. The completed sys-
tem produces an individual loan prediction, generates two explanations, computes deﬁned
explanation checks, and presents the resulting information through a web interface.
3.2
Existing System
Conventional credit scoring commonly uses structured application and repayment features
with statistical or machine-learning classiﬁers. A model may return a class and probability,
but an applicant-facing or oﬃcer-facing workﬂow also needs data validation, understandable
reasons, persistence, and a way to inspect prior evaluations. Post-hoc explainers can con-
tribute to this workﬂow, but they should not be assumed valid without a stated evaluation
procedure.
3.3
Limitations of a Prediction-Only Approach
A prediction-only interface omits important context: whether input values were normalized,
which features inﬂuenced the local result, whether multiple explanation methods agree, and
how stable an explanation is after a deﬁned perturbation. Likewise, presenting one scalar
called conﬁdence can be misleading if users interpret it as probability calibration or as trust
in the explanation. The system therefore returns separate prediction and explanation-quality
ﬁelds and labels the composite score as a project-deﬁned indicator.

3.4
Implemented System
TrustFin AI provides two loan products, each with its own XGBoost model, preprocessor,
engineered ﬁnancial features, and explanation background sample. A FastAPI route normal-
izes an application, calculates monthly EMI and FOIR, gets a model prediction, generates
SHAP and LIME explanations, evaluates the four conﬁgured checks, creates a dossier iden-
tiﬁer, and attempts to persist an evaluation record. The React client presents an applicant
view and a bank-oﬃcer view. Saved records can be inspected in history, batch CSV records
can be processed, and a ReportLab service generates a PDF assessment report.
3.5
Advantages
The system makes the prediction and explanation stages inspectable in one workﬂow.
Product-speciﬁc ﬁelds prevent property-collateral features from being treated as personal-
loan ﬁelds and keep revolving-credit and loan-purpose ﬁelds speciﬁc to unsecured lending.
Multiple explanation checks expose more information than a single attribution chart. Lo-
cal SQLite support allows use without a hosted PostgreSQL service. The record schema
preserves input JSON and model outputs for later inspection.
These advantages are bounded by the generated datasets, one stored split per model,
local metric deﬁnitions, and the absence of server-side authentication. TrustFin AI is a
completed academic project; its synthetic-data evaluation and access-control design deﬁne
its intended operating scope.

5.4
Data Preprocessing
The training scripts read a product CSV, compute derived features, separate Loan_Status
from the predictors, and drop Loan_ID. The target is mapped to 1 for Approved and 0
for Rejected. An 80/20 stratiﬁed train-test split is created with random state 42. The
preprocessor uses a column transformer: categorical ﬁelds pass through a one-hot encoder
with the ﬁrst category dropped and unknown values ignored; numerical ﬁelds pass through
standard scaling. The transformer is ﬁt on the training set and then applied to the test set.
For online requests, Pydantic schemas normalize optional numeric values and the model
registry ﬁlls product-speciﬁc defaults. This normalization is operationally convenient but
means omitted values can be replaced with defaults; users should provide valid application
data and review the displayed submitted form. Batch processing applies row-level normal-
ization and records rows that cannot be used as ﬂawed records with explanations of the
validation issue.

5.9
SHAP Implementation
The model registry initializes a SHAPExplainer backed by shap.TreeExplainer for each
XGBoost classiﬁer. For each application the transformed feature vector is passed to the
explainer. The implementation extracts the contribution vector, maps the sign to positive,
negative, or neutral direction, and returns one feature record for each transformed model
feature. Local contribution values are in the SHAP output space used by the explainer;
they are not percentages of approval probability. Displaying raw values for one-hot and
engineered features requires care because the feature name may not match a raw applicant
ﬁeld.

mode. The explainer receives the transformed training background and model feature names.
When explaining an input, it calls the classiﬁer’s predict_proba function and requests
contributions for the approved class. The route sets a deterministic seed derived from the
input JSON using SHA-256 before running LIME. This supports repeatable sampling for

7.4
Evaluation Metrics
Accuracy measures the fraction of correct class predictions. Precision measures the frac-
tion of approved predictions that are correct, and recall measures the fraction of actual
approved records identiﬁed by the classiﬁer.
F1 is the harmonic mean of precision and
recall. ROC-AUC measures ranking discrimination over thresholds. Since this is a credit
decision-support system, none of these measures alone captures ﬁnancial harm, calibration,
operational policy, or fairness. The dataset construction and class decision threshold must
be considered alongside the reported values.
7.5
Group Approval-Rate Ratios
The training scripts also calculate the ratio of the test-set female approval rate to the
male approval rate. The stored values are 0.9058 for home loans and 0.8648 for personal
loans. These are descriptive ratios on synthetic test records using the model’s predicted
approvals. The repository does not document a legal threshold for these values, and they do
not replace the per-applicant gender-ﬂip score used by the online Trust Score. They should
not be presented as proof of fairness.

Explanation Validation Results
Faithfulness, stability, consistency, and the individual counterfactual score are calculated
for an application response. TrustFin AI then computes the weighted Trust Score as docu-

they are not a controlled, de-identiﬁed experimental dataset.
The implementation has useful limitations to keep in view. The faithfulness mapping in-
cludes ﬁxed thresholds and a calibrated score band; stability perturbs standardized features
with one Gaussian scale; consistency compares only the top three names and not their signs;
and the fairness score ﬂips one attribute for one record. These measures are complementary
diagnostics, but combining them does not remove their individual assumptions.

7.8
Trust Score and Conﬁdence Score Analysis
The Trust Score measures the weighted combination of the four project-deﬁned explanation
checks. Prediction conﬁdence represents the probability assigned to the predicted class. A
high prediction conﬁdence does not imply high explanation reliability, and a high Trust Score
does not imply that the model’s prediction is correct or fair. The application’s result screen
should display these measures as distinct ﬁelds.
Product metric artifacts do not report
calibration error, Brier score, or reliability diagrams, so probability calibration cannot be
assessed from the available outputs.

Chapter 9
Conclusion and Future Scope
9.1
Conclusion
TrustFin AI implements a loan decision-support workﬂow that links home-loan and personal-
loan models with SHAP and LIME explanations, four explanation checks, a weighted Trust
Score, a React dashboard, database persistence, batch evaluation, and PDF reporting. The
product models use generated synthetic records and show high stored metrics on stratiﬁed
hold-out splits. These results are useful for demonstrating the system workﬂow, but they
do not establish real-world underwriting performance.
The project makes an engineering contribution by presenting the prediction and explana-
tion checks as separate outputs within one application. It also makes several assumptions
visible: the faithfulness score is heuristically calibrated, stability depends on a speciﬁed per-
turbation, consistency compares a top-three feature set, and fairness is measured through
an individual gender-ﬂip probability diﬀerence. The conﬁdence value is the predicted-class
probability and is not independently calibrated. These distinctions support an accurate
interpretation of the completed system.
9.2
Project Contributions
The implemented contributions are:
• two product-speciﬁc feature and preprocessing pipelines for home and personal loans;
• XGBoost training and saved test metrics for generated datasets;
• local TreeSHAP and tabular LIME explanation paths;
• code-level metrics for faithfulness, stability, top-feature consistency, and individual coun-
terfactual sensitivity;
• a weighted Trust Score and a separate predicted-class probability ﬁeld;
• a web interface, evaluation and batch history, local SQLite fallback, and on-demand PDF
reporting.

9.3
Limitations
The principal limitations are synthetic-only data, limited external validation, no probability
calibration, no group-level fairness audit in the request path, no causal explanation guar-
antees, and a custom composite score without external validation. The application does
not implement authentication or server-enforced role access. The what-if calculator changes
aﬀordability inputs but does not request a fresh model prediction. The project also has no
stored product-speciﬁc confusion matrices or held-out aggregate Trust Score study.
9.4
Future Scope
Future work should ﬁrst evaluate the models on a lawful, representative, de-identiﬁed lend-
ing dataset and establish leakage controls, missing-data policy, calibration, subgroup met-
rics, and temporal validation. Explanation metrics should be tested against independently
justiﬁed perturbation schemes and human review, with sensitivity analyses for thresholds
and weights. The Trust Score should be treated as a hypothesis until an evaluation study
demonstrates how it relates to meaningful explanation quality or reviewer decisions.
The application could add authentication, server-side authorization, privacy controls,
audit retention policies, versioned database migrations, secure deployment conﬁguration,
monitoring, and clear human-review workﬂows. The what-if calculator could call a controlled
scenario endpoint if the intended behavior is to recompute model output; such a change
would require displaying the changed inputs and preventing the scenario from being mistaken
for an approved loan. Additional explainers or constrained counterfactual methods may be
evaluated as future research, not described as existing functions.
9.5
Closing Statement
The completed implementation brings loan prediction, local explanation, explanation valida-
tion, history, batch processing, and reporting into one decision-support system. Its contribu-
tion is the integration of those functions with explicitly deﬁned diagnostics and an interface
for reviewing results. Extension to real lending operations would require institution-speciﬁc
data governance, security controls, external model validation, and human evaluation.
